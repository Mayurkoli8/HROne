# REVIEW.md

Line numbers refer to the original starter `app/main.py`. "UTC server" means the app runs on a machine whose local time zone is UTC (typical for containers / CI).

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | module setup, L22 `MongoClient(...)` | No `tz_aware=True`, so PyMongo returns naive datetimes, while `compute_overtime` builds IST-aware ones. Naive and aware values get mixed. | Read a punch back from MongoDB and pass it to `compute_overtime` -> `TypeError: can't subtract offset-naive and offset-aware datetimes` -> 500. | Client created with `tz_aware=True`; every instant in the code is an aware UTC datetime and is only converted to IST for the rule checks. |
| 2 | module setup / startup | No indexes are created at all. Nothing enforces unique `emp_code` or one record per (`emp_code`, `date`), and every list/analytics query is a collection scan. | `explain` on `GET /attendance` shows `COLLSCAN`; duplicate employees / punch-ins under parallel requests (see 12, 19). | Indexes created idempotently in the FastAPI lifespan (unique `emp_code`, unique `(emp_code, date)` and the query indexes listed in DECISIONS.md). |
| 3 | `compute_late_minutes`, L35 | Shift start is built with `punch_in.replace(hour, minute)` in whatever zone `punch_in` is in (naive server-local), not IST. | On a UTC server a 10:05 IST punch-in (04:35 UTC) gives `late_minutes = 0` instead of 35. | Shift start is built as `{attendance date}T{shift_start}` in IST and compared with the aware punch instant. |
| 4 | `compute_late_minutes`, L36-37 | The grace check is done on the *truncated minute count* (`minutes > 10`), so anything from 10:00 to 10:59 after shift start is never late. R2 says late is strictly more than 10:00. | Shift 09:30, punch-in 09:40:30 -> 0, expected 10. | Compare seconds: late only when `seconds > 600`, then `seconds // 60`. |
| 5 | `compute_late_minutes` | Overnight shifts: the shift start is taken on the punch's own calendar day. | Shift 22:00-06:00, punch-in 00:30 -> 0, expected 150 (the shift started 22:00 the previous day). | Late is measured from the shift start on the record's attendance date (R1), so it uses the previous day for these punches. |
| 6 | `compute_work_hours`, L41 | `round()` is float rounding (banker's rounding on exact halves), not half-up (R4). Around 4.50 this also flips `half_day`. | `Decimal(seconds) / 3600` quantized with `ROUND_HALF_UP`; instants are truncated to whole seconds when they enter the API. |
| 7 | `compute_overtime`, L47 | No 30-minute minimum (R3). | Shift end 18:30, punch-out 18:35 -> 5, expected 0. | Return the minutes only when they are `>= 30`, else 0. |
| 8 | `compute_overtime`, L46 | For an overnight shift the end is on the *next* day, but the helper always uses `date_str`. | Shift 22:00-06:00, date 2026-07-06, punch-out 06:40 on the 7th -> 1480, expected 40. | One day is added to the shift end when `shift_end <= shift_start`. |

| 10 | `PunchInIn`, L65-66 | `punched_at: Optional[int]` accepts seconds, numeric strings and whole floats (lax mode). `status: str` accepts anything, including `ABSENT`/`LEAVE`. | `"punched_at": 1783312500` (seconds) creates a record in January 1970. `"status": "ABSENT"` returns 201. | `punched_at` is a strict int between 100000000000 and 4102444800000, otherwise 422; `status` is `Literal["PRESENT", "WFH", "ON_DUTY"]`. |

## Looked at and decided it is not a defect

- `load_dotenv()` (L20): by default it does not override variables that already exist, so real environment variables win, as the contract asks.
- `doc.pop("_id", None)` after `insert_one` (L84): `insert_one` adds `_id` to the dict, so removing it is right. The real problem is that the rest of the response isn't formatted (13).
- `int(...)` truncation in `compute_overtime` (L47): for positive minutes `int()` equals floor, and negatives are clamped by `max(0, ...)`, so the floor part is fine. The bugs there are the threshold and the overnight end (7, 8).
- `compute_work_hours` subtracting the two instants is correct once both are aware. Only the rounding is wrong (6).
- Status codes 201 on create / punch-in and 409 for duplicates match the contract. Only the way duplicates are detected is unsafe (12, 19).
- The `IST` constant (`UTC+05:30`) is correct and is reused.
